⛔ 三大绝对禁令

碰了就翻车的红线，任何情况下都不能违反

  • 1. 禁止覆盖列表页
    latest.html、index.html 绝对禁止全量覆盖，必须「读取 → 插入 → 保存」
  • 2. 禁止自制模板
    所有页面必须用Pro生成器或标准模板，不许从零写HTML，防止样式不统一
  • 3. 禁止虚假数据
    价格数据必须查当日真实数据，非交易日不生成报告，数据必须双源验证

💥 历史教训案例库

历次升级踩过的坑，绝不能再踩第二次

🎨 白卡白字惨案

2026-06-14 | 现象：.card-glass 白色背景样式优先级过高，覆盖了头部深色样式，导致文字看不清
根因：CSS优先级处理不当，后加载的样式覆盖了前面的
教训：所有组件必须在深色主题下测试对比度，背景色和文字色必须有足够对比度

📋 列表页被报告覆盖事故

2026-06-16 | 现象：日报生成器直接输出到 latest.html，把列表页覆盖成了报告页
根因：职责不清，报告生成器和列表页维护脚本写同一个文件
教训：报告输出必须用 YYYYMMDD_报告名.html 命名，列表页由独立脚本维护，严格职责分离

📊 指数代码混淆bug

2026-06-15 | 现象：000001既是上证指数也是平安银行，没区分类型导致数据完全错误
根因：API调用时没有传入类型参数，默认按股票查询
教训：所有金融数据必须区分类型（指数/股票/基金），API调用必须显式传 type 参数

🔧 self.data_dir 缺失bug

2026-06-16 | 现象：日报、盘后速递的题材模块不显示，数据为空
根因：基类 ProGenerator 不保存 data_dir 属性，子类 _load_data() 依赖该属性但未正确传递
教训：基类必须保留所有必要上下文，子类 super() 调用顺序要正确，参数传递要完整

🏗️ 推倒重来的陷阱

现象：每次升级都想从头重写，导致旧功能丢失、新bug不断
根因：追求完美主义，忽视了现有系统的稳定性和历史债务
教训：系统升级不是重构，旧版本模块不能少，必须在现有架构上渐进式迭代

🔄 Git合并冲突灾难

现象：使用 git merge -X theirs 自动解决冲突，导致页面残留 <<<< 冲突标记
根因：图省事用自动合并，不检查结果
教训：禁止自动合并策略，冲突必须手动解决，合并后必须检查文件内容

📱 移动端适配遗漏

2026-06-04 | 现象：新功能在PC端正常，手机端样式错乱
根因：只测了PC端，忽略了移动端适配
教训：所有UI变更必须同时验证PC端和移动端，响应式是必选项

⚡ 先 build 后 render 顺序

现象：Pro报告生成空白页
根因：直接调用 render()，没有先调用 build_standard_report() 填充内容
教训：Pro生成器必须严格按「实例化 → build → render/publish」顺序调用

✅ V4 升级必须遵守的架构原则

从历史教训中提炼的设计原则，贯穿整个升级过程

渐进式升级

不推翻、不重构，逐个模块迁移。每个模块独立验证通过后再推进下一个

新老并行

旧版本继续可用，新功能先灰度验证。确认稳定后再逐步减少对旧版本的依赖

向下兼容

数据格式、API接口、文件命名必须兼容旧版，不能破坏现有工作流

质量优先

数据准确性 > 功能丰富度 > 视觉效果。速度让位于质量，不能为了快而出错

职责分离

数据层、内容层、展现层严格分离，各司其职。跨层调用必须通过明确的接口

可回滚

每次升级都必须有回滚方案。出问题时能在5分钟内恢复到升级前状态

测试先行

每个模块上线前必须经过：单元测试 → 集成测试 → 真实数据验证 → 灰度观察

文档同步

代码和文档同步更新。架构变更必须同步更新架构图和说明文档

🎯 各阶段风险点与验收检查清单

每个阶段完成后必须逐项检查，全部通过才能进入下一阶段

Phase 1: 摸底与规范化阶段

✅ 验收检查点：
  • 完整的系统架构图，各模块关系清晰
  • 代码库文档（DeepWiki）覆盖所有核心模块
  • 设计规范文档化，组件标准统一
  • 现有所有bug清单化，优先级明确
⚠️ 主要风险：摸底不全面，遗漏边缘模块 → 后果：后续升级踩坑

Phase 2: 数据层升级阶段

✅ 验收检查点：
  • 数据库Schema设计文档完整，字段定义清晰
  • JSON → DB 迁移工具开发完成，数据100%准确
  • 旧的JSON文件读写仍然可用（向下兼容）
  • 数据访问层（DAL）封装完成，上层无感知
  • 数据一致性校验机制就位（双写校验）
⚠️ 主要风险：数据迁移丢失/错误 → 后果：历史数据丢失，报告出错
⚠️ 主要风险：数据库性能不达标 → 后果：页面加载变慢，影响体验

Phase 3: 内容引擎建设阶段

✅ 验收检查点：
  • 五大内容引擎（市场/股票/题材/持仓/催化）全部开发完成
  • 输出的结构化内容模型定义清晰，字段完整
  • 与现有分析结果做对比，准确率不低于现有水平
  • 内容质量评分系统就位
  • Skill整合完成，数据源可追溯
⚠️ 主要风险：分析口径不一致 → 后果：同一数据不同页面显示不同
⚠️ 主要风险：内容引擎质量不如旧版 → 后果：报告质量下降

Phase 4: 展现层重构阶段

✅ 验收检查点：
  • V4组件库完整，覆盖所有常用组件
  • 亮/暗主题切换正常，无白卡白字问题
  • PC端和移动端响应式适配正常
  • 所有报告类型都有V4版本，功能不缺失
  • 导航栏、列表页、详情页跳转链路完整
⚠️ 主要风险：样式不统一，白卡白字重现 → 后果：用户体验差
⚠️ 主要风险：旧功能在V4版中缺失 → 后果：功能退化

Phase 5: 平滑迁移与收口阶段

✅ 验收检查点：
  • 所有日常报告切换到V4生成，结果验证通过
  • 每日自动更新流程适配V4
  • 企业微信推送链接正确，可访问
  • 旧版本归档，代码保留，但不再更新
  • 完整的V4系统文档就位
⚠️ 主要风险：切换后出现重大bug → 后果：影响日常使用
⚠️ 主要风险：回滚方案失效 → 后果：出问题无法快速恢复

🔴 数据质量红线

数据是系统的生命线，任何情况下不能突破这些底线

  • 价格数据必须查当日最新，禁止使用历史数据填充
  • 双数据源必须同步验证，不一致时取保守值并告警
  • 指数和股票必须区分类型，代码不能混淆
  • 非交易日不生成交易类报告（日报/盘中/盘后）
  • 所有数据必须标注来源，传闻必须标注可信度
  • 数据异常值必须二次验证（如涨跌幅超过±10%）
  • 持仓数据必须与实际一致，4只持仓不能多也不能少

🚀 每次上线前必查清单

任何改动上线前，逐项打勾确认

  • 白卡白字检查：所有页面没有浅色背景+浅色文字组合
  • 导航栏检查：11个按钮完整，跳转正确，"周三前瞻"名称统一
  • 列表页保护：latest.html / index.html 没有被全量覆盖
  • 移动端适配：手机端浏览正常，没有横向滚动条
  • 数据验证：关键数据（指数、持仓）与真实行情一致
  • 链接检查：所有内部链接可正常跳转，没有404
  • Git状态：工作区干净，没有未提交的冲突文件
  • 回滚方案：确认可以快速回退到上一版本
